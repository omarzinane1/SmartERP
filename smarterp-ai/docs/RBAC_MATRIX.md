# SmartERP AI — permissions, rôles et scopes

Audit du 27 septembre 2026. Les codes et sources de la matrice finale sont **IMPLEMENTED côté frontend**. Leur enforcement Django est **BACKEND REQUIRED**. Les attributions de production proposées ci-dessous ne doivent pas être confondues avec les rôles de démonstration.

## Trois contrôles distincts

1. Session authentifiée : `RequireAuth` vérifie un booléen Zustand.
2. Permission de fonction : `permissions.includes(code)` dans la page, le hook ou la navigation ; les réponses métier ont souvent leur propre tableau de permissions.
3. Droit sur l'objet et transition : `capabilities.canEdit/canPost/canPay/...`, `canAssign`, `allowedApprovalTypes`, `grantable`, `lockedFields`, module actif.

Un bouton visible exige parfois plusieurs conditions ; un bouton masqué ne sécurise jamais un endpoint. Django doit vérifier la permission, le scope, les relations et la transition à chaque requête, y compris les sous-ressources, exports et appels d'outils IA. Une capability absente doit refuser l'action sensible. Les mocks ne sont pas une autorité de sécurité.

Les contrôles des listes et des détails ne sont pas uniformes. Des sous-requêtes sont activées après lecture des permissions parentes ; d'autres requêtes principales partent avant que le frontend connaisse les droits. Le serveur doit filtrer dès la sélection SQL, sans retourner les lignes interdites pour que React les cache ensuite.

## Rôles réellement présents

Source : `src/features/admin/data/admin.mock.ts`. Huit rôles : **Owner, Admin, Manager, Commercial, Comptable, Acheteur, Stock, Analyste personnalisé**. Les sept premiers sont `system: true`, non modifiables. Owner n'est pas attribuable/duplicable par l'admin de démo. Le rôle custom est éditable et dupliqué avec uniquement les permissions grantable. Le catalogue refuse l'octroi de `users.manage`, `roles.manage`, `roles.assign`, `audit.export` dans les mutations de rôle mock.

L'algorithme `action` du catalogue transforme beaucoup d'actions non listées en `edit`, et des codes IA en `ai`. Il n'est pas une définition produit des rôles. Il est particulièrement impropre à servir de migration de rôles de production. La chaîne `AuthUser.role` ne calcule pas les permissions : le frontend se fie aux tableaux reçus. Le mock admin n'écrit pas automatiquement dans ces tableaux des autres features.

## Architecture Django recommandée — PROPOSED

`User` global → `Membership(user, company, department, status)` → `MembershipRole(role, scope_kind, department?, owner_only?, warehouse?)` → `RolePermission` → `Permission(code unique)`. Les rôles sont liés à une société ; les rôles système sont créés à partir de templates versionnés et protégés. Une seule attribution principale suffit au premier livrable si l'UI n'affiche qu'un rôle ; la relation permet l'évolution sans modifier l'identité utilisateur.

Résoudre `request.company` depuis la session et une membership active. Un `company_id` dans l'URL `/companies/:id/modules/...` doit égaler le contexte autorisé ; ce n'est jamais un sélecteur libre. Le scope département/commercial/acheteur/dépôt est une restriction additionnelle sur le queryset, pas un rôle global Django ni un filtre client facultatif.

Pipeline proposé : authentification → société/membership → module actif → permission d'action → queryset scoped → validation FK même société → règle d'objet et transition → transaction → audit. Préférer `404` pour un identifiant d'une autre société afin de ne pas révéler son existence ; `403` pour une action interdite sur une ressource du contexte connu. Le profil est toujours celui de `request.user`.

`can_grant(actor, code, scope)` doit empêcher d'accorder plus que ce que l'acteur peut déléguer ; posséder un droit ne suffit pas forcément à le déléguer. Interdire l'élévation de son propre rôle, la suppression du dernier Owner, la modification d'un rôle système et le changement de société d'un objet. La version de rôle protège les éditions concurrentes. Recalculer permissions/capabilities et invalider caches/sessions concernés après changement.

## Lacunes du catalogue

L'inventaire inclut les codes présents seulement dans un type, seulement dans un catalogue ou effectivement testés dans une page. Ces catégories sont indiquées en annexe. `analytics.view` et `cashflow.view` ne doivent pas être fusionnés arbitrairement avec `reports.view`/`finance.view`. `invoices.credit_note` n'a pas d'endpoint d'avoir. `ai.tools.finance` et `ai.tools.inventory` sont des droits/outils de simulation, pas des outils Django déjà disponibles. Le catalogue admin est une union de quelques listes mocks : les codes des clients, devis, paiements, fournisseurs et certains domaines ne sont pas tous repris. Créer une migration unique des permissions fondée sur cette matrice complète, puis décider explicitement les codes à déprécier.

Les sources `*.types.ts` prouvent qu'un code est accepté par le type, pas qu'un bouton l'utilise. La colonne Action et les chemins de composants/hooks permettent de voir la différence. La colonne Scope de la matrice est une **recommandation backend**, pas une isolation démontrée par le navigateur.
